## 一、项目简介（面试版）

### 1.1 一句话版本

NebulaMind 是一个面向个人与团队的 AI 智能云盘产品，解决“文件检索难、整理慢、内容利用率低、安全管控弱”四个问题，核心链路是“上传 → 理解 → 检索 → 生成”。

### 1.2 30 秒版本

我是 5 人团队、8 周 AI 智能云盘项目 NebulaMind 的核心成员（架构师/后端负责人），同时参与需求拆解、范围管理、任务协调和文档交付。产品定位是把传统云盘从“存储工具”升级为“知识助手”：用户上传文档后，系统自动分类打标、生成摘要、建立向量索引；用户可以用自然语言搜索文件、对文档提问，还能直接生成报告和 PPT。最终交付了 14+ 个后端 Controller、40+ 个 REST 接口、7 个前端页面，以及 Docker 容器化和完整部署方案。

### 1.3 90 秒版本

NebulaMind 的核心问题是：传统云盘只解决“存”，不解决“找”和“用”。我们通过用户访谈和场景分析，锁定个人知识工作者、研究团队、企业安全管理员三类用户，定义出四个核心场景：自动整理、语义检索、基于文档的 AI 问答与内容生成、敏感信息防护。

产品最终形成完整闭环：文件上传后，后端写入 MinIO 对象存储，通过 RabbitMQ 通知 AI 服务异步解析内容，生成分类、标签、摘要，并把文本切片向量化后写入 Milvus；用户在搜索框用自然语言提问，系统先做向量检索，再交给大模型生成回答；同时支持版本历史、diff、回滚，支持 S3/WebDAV 云盘接入，支持敏感检测和 AES-256-GCM 加密。

我的实际角色是架构师/后端负责人，同时参与需求优先级、范围控制、迭代排期、跨角色协调和交付验收等产品/项目管理工作。过程中最大的产品决策是：原计划接入联通云盘官方 API，但个人账号无法获得凭证，我们及时把范围调整为 S3/WebDAV 兼容接入，没有影响核心交付；最大的工程风险是 AI API 限流和模型可用性，我们用异步处理、失败降级和重试机制解决。

## 二、项目完整链路

### 2.1 用户价值链路

| 环节 | 用户痛点 | NebulaMind 的解法 | 交付能力 |
|------|---------|------------------|---------|
| 存储 | 文件分散、没有统一入口 | 统一云盘 + 本地存储抽象 | 文件上传、下载、删除、重复检测 |
| 整理 | 手动分类打标耗时 | AI 自动识别类型、生成分类与标签 | 文件解析、AI 分类、标签生成 |
| 查找 | 关键词搜索不到相关内容 | 语义检索，用自然语言找文件 | Embedding + Milvus 向量检索 |
| 理解 | 文档太长、读不完 | AI 摘要、要点提炼、文档问答 | 单/跨文档 RAG 问答、摘要 |
| 生产 | 素材难以复用 | 基于文件直接生成报告、PPT | 内容生成、格式转换 |
| 协作 | 版本混乱、改错难追溯 | 版本历史、diff、回滚 | 文件版本管理 |
| 安全 | 敏感信息容易泄露 | 敏感检测 + 加密 + 权限/审计 | 两级检测、AES-256-GCM、端到端加密 |
| 生态 | 已有网盘/对象存储无法打通 | S3/WebDAV 协议接入 | 云存储配置、浏览、上传、导入 |

### 2.2 端到端业务链路

```
用户注册/登录
    ↓
上传文件（前端进度条 → 后端 → MinIO → PostgreSQL 元数据）
    ↓
RabbitMQ 异步任务 → AI 服务解析文件内容
    ↓
生成分类 / 标签 / 摘要 / 向量切片
    ↓
Milvus 写入向量索引，PostgreSQL 写入文本分片
    ↓
前端通过 SSE 收到 AI 处理完成状态
    ↓
用户操作：
  语义搜索 → 向量召回 → 返回文件
  文档问答 → 检索切片 → LLM 生成答案
  内容生成 → 摘要 / 报告 / PPT
  安全检测 → 风险分级 → 自动加密
  版本管理 → 新版本 / diff / 回滚
  云盘导入 → S3/WebDAV 文件导入本系统并继续走 AI 链路
```

### 2.3 技术链路（面试重点）

#### 链路 A：文件上传与 AI 处理

```
浏览器
  → POST /api/v1/files/upload（Axios，带上传进度）
  → FileController
  → FileService.createFile
      1. 计算 SHA-256，做重复检测
      2. 生成对象路径，写入 MinIO/S3
      3. 保存 File 元数据到 PostgreSQL
      4. 发送 RabbitMQ 上传事件
  → AI 服务 FileProcessor 消费事件
      1. 按扩展名/MIME 解析内容（PDF/Word/表格/图片/PPT/压缩包等）
      2. 文本分片
      3. 调用 Embedding 模型生成向量
      4. 写入 Milvus
      5. 写回分类、标签、摘要、AI 状态
  → 前端通过 SSE 收到处理结果
```

要点：上传是同步接口，AI 处理是异步链路，避免大文件等待；失败时 AI 状态标记失败，前端可重试。

#### 链路 B：语义搜索

```
用户输入自然语言
  → 前端 POST /api/v1/search
  → SearchController
  → AI 服务 /search
      1. 用户问题向量化
      2. 在 Milvus 中做相似度检索
      3. 可选 Rerank 重排序
      4. 返回文件列表 + 摘要/片段
  → 前端展示结果
```

关键词搜索是“字面匹配”，语义搜索是“意思匹配”，例如搜“上周的项目周报”也能命中包含相关语义但文字不完全一致的文档。

#### 链路 C：文档问答（RAG）

```
用户选择单个或多个文件
  → POST /api/v1/qa 或 /api/v1/qa/cross
  → QAController
  → AI 服务 RAG 链路
      1. 把问题向量化
      2. 在 Milvus 检索相关文本切片（Top-K）
      3. 把切片拼成上下文 Prompt
      4. 调用大模型生成答案
      5. 返回答案 + 来源引用
  → 前端展示回答与引用
```

RAG 的优势：不需要重新训练模型，答案基于用户自己的文件，可溯源，也更容易控制权限。

#### 链路 D：内容生成

```
用户选择文件
  → POST /api/v1/generate/summary | extract | report | ppt
  → GenerateController
  → AI 服务
      1. 读取文件内容或向量切片
      2. 使用不同 Prompt 模板生成摘要/要点/报告/PPT 大纲
      3. 结构化返回
  → 前端展示或下载
```

#### 链路 E：安全检测与加密

```
上传完成或用户手动触发
  → POST /api/v1/security/detect
  → 第一级：正则快速筛查（身份证、手机号、密钥等）
  → 第二级：LLM 深度分析，输出敏感等级 normal/low/medium/high
  → 高风险文件触发 AES-256-GCM 加密（服务端密钥）
  → 用户可选择端到端加密：浏览器本地生成密钥并加密，密钥仅显示一次
  → 解密后才能下载/查看
```

关键设计：加密的是存储内容，数据库仍保存元数据；端到端加密时服务端不持有明文和密钥，符合“数据最小暴露”原则。

#### 链路 F：版本管理

```
用户上传新版本
  → POST /api/v1/files/{fileId}/versions/upload
  → FileVersionService
      1. 新文件写入 MinIO
      2. 生成新版本记录
      3. 记录大小、哈希、操作者、时间
  → 用户查看版本历史
  → diff 对比（文本类文件比较内容差异）
  → 回滚到指定版本时恢复对应对象内容
```

#### 链路 G：S3/WebDAV 云盘接入

```
用户新增云存储配置（S3 或 WebDAV）
  → POST /api/v1/storage-config
  → 测试连接 /api/v1/storage-config/{id}/test
  → 浏览远端文件 /drive/files
  → 上传/下载/删除远端文件
  → 导入远端文件 /drive/files/import
      1. 下载远端内容
      2. 按扩展名识别文件类型与 MIME（docx/xlsx/pptx/pdf 等）
      3. 写入 NebulaMind 文件体系
      4. 继续走 AI 处理链路
```

### 2.4 数据链路

| 数据 | 存在哪里 | 作用 |
|------|---------|------|
| 用户、权限、文件元数据、版本、审计日志 | PostgreSQL | 业务主数据 |
| 文件原文 | MinIO / S3 | 对象存储，保存二进制内容 |
| 解析后的文本分片 | PostgreSQL file_contents | 全文检索与 RAG 上下文 |
| 向量 | Milvus | 语义相似度检索 |
| Token、会话、缓存 | Redis | 登录态与热点缓存 |
| 异步任务 | RabbitMQ | 上传后 AI 处理、删除事件等 |
| 操作记录 | AuditLog | 安全审计与追踪 |

## 三、项目经理面试准备

### 3.1 我的角色与贡献

建议如实表述：

> 我在项目中是架构师/后端负责人，同时参与产品与项目管理相关工作：需求拆解、优先级排序、任务协调、里程碑跟进、交付验收和文档沉淀。

可以讲的 PM 相关动作：

- 用用户故事 + 验收标准定义“做完”的标准
- 用 WBS 拆任务，按角色分配
- 按周迭代，V1.0 → V2.0 每版有明确目标
- 遇到外部依赖不可用（联通云盘 API）时做范围调整
- 遇到 AI API 限流时设计异步、重试、降级方案
- 项目文档齐全，能随时交接

### 3.2 项目经理高频问题与参考思路

#### Q1：介绍一下这个项目

不要从技术栈开始，先讲背景、目标、用户、范围、我的角色、结果。

回答框架：
1. 项目背景：传统云盘只存不用，检索难、整理慢、内容利用率低
2. 项目目标：做一个 AI 驱动的知识管理云盘，形成上传→理解→检索→生成闭环
3. 团队与周期：5 人，8 周
4. 我的角色：架构/后端负责人 + 需求拆解与交付管理
5. 结果：核心功能全部交付，容器化完成，文档完整

#### Q2：项目周期为什么是 8 周？怎么排的？

参考回答：
- W1：需求分析与范围确认
- W1-W2：架构设计、数据库设计、技术选型
- W2：团队分工与任务拆解
- W3-W6：迭代开发，V1.0 基础能力 → V1.1 AI 能力 → V1.2 生成与安全
- W6-W7：测试、性能优化、安全加固
- W7-W8：Docker 容器化、部署方案与文档交付
- 排期时按依赖关系排：先搭后端基础，再联调 AI，最后做前端完整体验

#### Q3：如果需求中途变化怎么办？

参考回答：
- 先做影响分析：变化影响哪些模块、哪些排期、哪些验收标准
- 用 MoSCoW 重新排序：新需求是不是 Must，能不能放下一版
- 必要的时候砍掉低优先级需求，保证核心链路不被破坏
- 及时同步团队和文档，避免口头变更
- 举例：联通云盘 API 拿不到个人凭证，我们把它从 Must 调整为 Won't，改为 S3/WebDAV，既满足“云存储接入”目标，又避免卡住交付

#### Q4：项目中最大的风险是什么？怎么控制？

建议从四类风险回答：
1. 外部依赖风险：AI API 限流、模型下架、账号凭证限制 → 异步队列、失败降级、重试、接口抽象
2. 技术风险：文件格式解析复杂、中文文件名乱码、向量检索效果不稳定 → 先做常见格式，再逐步扩展；导入时按扩展名/MIME 识别
3. 团队交付风险：角色多、联调复杂 → 接口契约先行、分阶段集成、文档交接
4. 部署风险：Docker 拉取慢、环境不一致 → 国内镜像源、镜像打包、Compose 统一编排

#### Q5：如何保证团队按计划交付？

参考回答：
- 任务拆到“一周能验证”的粒度
- 每个版本有明确的验收标准
- 每周检查进度，遇到阻塞及时调整
- 接口文档和开发方案提前对齐，减少联调返工
- 交付前做功能清单核对

#### Q6：你和开发/前端/AI 工程师怎么配合？

参考回答：
- 先定接口契约：后端给接口，前端按接口开发，AI 服务按统一协议返回
- 文档先行：API 规范、数据结构、状态码统一
- 分阶段联调：后端自测 → 前后端联调 → AI 联调 → 端到端测试
- 遇到问题按优先级处理，核心链路优先

#### Q7：项目为什么用异步消息队列？

参考回答：
- 文件解析和 AI 处理耗时长，不能阻塞上传接口
- RabbitMQ 可以削峰、解耦、失败重试
- 上传成功后立即返回，AI 处理结果通过 SSE 通知前端
- 如果 AI 服务暂时不可用，任务留在队列中，不会丢

#### Q8：如果重做这个项目，你会改什么？

参考回答：
- 更早定义产品指标，比如搜索成功率、AI 处理成功率、用户留存
- 第一版就接埋点和监控，而不是最后补
- 先做最小闭环，再扩展格式和云盘协议
- 增加自动化测试覆盖，特别是 AI 降级场景
- 提前评估外部 API 的可用性和限流，避免临时换方案

### 4.2 产品经理高频问题与参考思路

#### Q1：为什么做这个产品？

参考回答：
- 用户痛点真实：文件多、找文件难、整理慢、内容不会自动复用
- 市场机会：AI 能力成熟，可以把云盘从工具变成知识助手
- 差异化：不只是存储 + 简单问答，而是全流程 AI 化
- 用三个用户画像说明需求来自真实场景

#### Q2：目标用户是谁？优先级怎么排？

参考回答：
- P0：个人知识工作者（咨询、研究、内容创作），单人高频使用
- P1：团队/研究组，需要共享、版本、权限
- P2：企业安全管理员，需要敏感检测和合规
- 第一版优先服务 P0，因为个人场景闭环最短、最容易验证

#### Q3：如果只能保留 3 个功能，你保留什么？

参考回答：
1. 文件上传与存储（基础）
2. 语义搜索（解决找文件难）
3. 文档问答（体现 AI 价值）
理由：这三个功能构成“存 → 找 → 用”的最小闭环，能验证产品假设。

#### Q4：如何判断这个产品做得好不好？

参考回答：
- 用户侧：搜索成功率、问答答案可接受率、AI 处理成功率

#### Q6：AI 会胡说八道，你怎么保证回答质量？

- 对高风险场景设置人工确认

#### Q7：如果用户反馈“搜索不准”，你怎么处理？

参考回答：
1. 先定义“不准”：是搜不到、排序不对，还是答非所问
2. 看日志和埋点：用户输入了什么，返回了什么，是否点击

4. 小步优化：调整分片、增加 Rerank、补充同义词/查询改写
5. 用测试集评估，避免“修一个坏一个”

## 五、技术理解面试准备（非技术岗也建议掌握）

### 5.1 高频问题与口语化答案

#### 1. 什么是前后端分离？

前端负责页面和交互，后端提供接口和数据。前端通过 HTTP 调用后端接口，各自独立开发、部署。NebulaMind 的前端是 React，后端是 Spring Boot。

#### 2. JWT 是什么？为什么不用 Session？

JWT 是一段包含用户信息的签名 Token，服务端验证签名即可，不需要在服务器保存会话。适合前后端分离、水平扩展。NebulaMind 用 JWT + Refresh Token，Access Token 短时有效，Refresh Token 用来续期，降低长期泄露风险。

#### 3. REST 是什么？

REST 是一种接口设计风格：用 URL 表示资源，用 HTTP 方法表示动作，例如 GET /files 获取文件、POST /files 上传文件、DELETE /files/{id} 删除文件。返回 JSON，状态码表达结果。

#### 4. SSE 和 WebSocket 有什么区别？

SSE 是服务端单向推送，适合 AI 流式输出、进度通知；WebSocket 是双向长连接，适合聊天、实时协作。NebulaMind 用 SSE 推送 AI 处理状态和流式回答。

#### 5. 什么是对象存储？为什么文件不直接放数据库？

数据库适合存结构化小数据；大文件用对象存储（MinIO/S3），按对象读写，支持高并发、大文件、成本低。数据库里只存元数据，例如文件名、路径、大小、哈希、MIME。

#### 6. 什么是 Embedding？

Embedding 是把文本/图片/文件转换成一组向量（数字数组），意思相近的内容向量距离近。NebulaMind 用 Embedding 实现语义搜索和问答检索。

#### 7. 什么是向量数据库？为什么需要 Milvus？

普通数据库按条件查询，向量数据库按相似度查询。Milvus 负责存向量和做 Top-K 近似检索，是语义搜索的底座。

#### 8. 什么是 RAG？为什么不用微调？

RAG（检索增强生成）先从知识库检索相关内容，再拼进 Prompt 让大模型回答。优点：不用训练、成本低、答案可溯源、内容更新快。微调适合改变模型风格或领域能力，但成本高、更新慢、不适合作为文件问答的主要方案。

#### 9. 什么是 Prompt？

Prompt 是给大模型的指令和上下文。NebulaMind 为分类、摘要、报告、PPT、敏感检测分别设计模板，让输出更稳定、更结构化。

#### 10. 什么是异步任务？为什么用 RabbitMQ？

异步任务是不阻塞主流程、稍后执行的任务。RabbitMQ 是消息队列，生产者发消息，消费者处理。文件上传后马上返回，AI 解析排队处理，失败可以重试。

#### 11. 什么是 Docker？为什么用 Docker Compose？

Docker 把应用和依赖打包成镜像，保证“本地和线上一致”。Compose 用配置文件一次性启动多个服务。NebulaMind 有 PostgreSQL、Redis、RabbitMQ、MinIO、Milvus、后端、前端、AI 服务，Compose 统一管理。

#### 12. AES-256-GCM 是什么？

一种对称加密算法，用同一个密钥加密和解密，256 位密钥强度高，GCM 同时保证完整性和防篡改。NebulaMind 用于敏感文件加密；端到端加密时密钥在浏览器本地生成，服务端不持有。

#### 13. RBAC 是什么？

基于角色的访问控制：用户分配角色，角色分配权限，避免给每个人单独配权限。NebulaMind 的权限模块基于此设计。

#### 14. 限流是什么？Sentinel 怎么用？

限流是控制接口在单位时间内的调用次数，防止系统被打爆。NebulaMind 用 Sentinel 对搜索、问答、生成等接口做限流熔断，AI 服务本身也有调用频控。

#### 15. S3 和 WebDAV 是什么？

S3 是对象存储协议，适合云存储服务；WebDAV 是基于 HTTP 的文件操作协议，适合网盘挂载和读写。NebulaMind 都通过配置接入，支持浏览、上传、下载、导入。

### 5.2 技术面试避坑提醒

- 不要夸大“部署上线”，目前 Docker 容器化和部署方案已完成，线上部署可说明“已具备条件/待执行”
- 不要说自己独立完成所有模块，团队项目强调协作

## 六、开放题与深度追问

### 6.1 如果给你三个月，你怎么把 NebulaMind 做成一个真正的产品？

回答框架：
1. 先定义成功指标：注册转化、上传后 AI 完成率、搜索成功率、7 日留存
2. 补数据能力：埋点、日志、看板
3. 做用户验证：找 20-30 个真实用户使用，收集反馈
4. 优先迭代：分享链接、移动端、多网盘接入
5. 完善工程：CI/CD、监控告警、自动化测试、HTTPS
6. 商业化验证：个人订阅 / 团队版 / 企业安全版

### 6.2 怎么向完全不懂技术的人解释这个项目？

参考话术：

> 你可以把 NebulaMind 理解成一个“会自己整理文件的云盘”。你把文件传上去，它自动帮你分类、打标签、写摘要；以后你不用记住文件名，用一句话描述就能找到；你还能直接问文件里的内容，比如“上个月的方案里预算是多少”，它会从文件里找到答案并告诉你出处。如果文件很敏感，它还会帮你检测和加密。

### 6.3 如果 AI 答错了，责任在谁？怎么避免？

参考回答：
- 责任在产品设计：不能把 AI 输出当成绝对事实
- 避免方法：RAG 基于原文、答案带引用、高风险场景人工复核、提示“AI 生成内容仅供参考”
- 迭代方法：把错误案例加入测试集，持续优化检索和 Prompt

### 6.4 你最满意的一个功能是什么？为什么？

建议选择“端到端文件加密”或“S3/WebDAV 云盘导入”。

端到端加密的理由：
- 真正解决用户安全诉求
- 密钥只在浏览器本地生成，仅显示一次，服务端不持有
- 需要权衡“易用性”和“安全性”，是典型产品决策

云盘导入的理由：
- 原方案联通云盘不可用，及时切换到 S3/WebDAV
- 解决中文文件名、格式识别、导入后继续走 AI 链路的问题
- 体现了范围管理和技术落地能力

### 6.5 你最失败/最困难的一件事？

建议讲“联通云盘 API 不可用”或“AI API 限流与模型不稳定”：

> 最初方案计划对接联通云盘官方 API，但个人账号拿不到凭证，等于外部依赖不可用。我们没有硬撑，而是重新评估目标：用户要的是“把已有网盘文件接进来”，不是一定要用联通云盘。于是把范围调整为 S3/WebDAV 兼容接入，用存储抽象层隔离差异，最终按时交付。这件事让我意识到：项目早期就要验证外部依赖，计划要留备选方案。

### 6.6 团队有人不配合/进度落后怎么办？

参考回答：
- 先了解原因：是任务不清、能力不足、外部依赖，还是个人问题
- 如果是任务不清，重新拆解并确认验收标准
- 如果是外部依赖，调整排期或降级方案
- 如果是长期问题，及时向上反馈并调整分工
- 关键原则：暴露问题越早，解决成本越低
